For a thing that wakes the phone for a call, that is not a residual you get to file under “reach, never correctness.”
- **Re-assertion is a fourth writer, and the register invariant as written does not cover it (Part 2, Part 3, question A — traced).** `_register` returns before the wire when `token == _registered`. Re-assert’s whole job is to `POST` that token. It cannot enter the 4-line block you promoted. “0 lines, every future `POST` site inherits” is prose, not a door; defect five was born as a second `POST` that did not re-check after `await`. Even if you copy the block: (1) it runs only on **success** — a `POST` that landed and then threw never `remember`s, which is the exact “may have landed” insight the repair used to justify POSTing on the failure path; (2) `_generation` answers session liveness, not token currency — a re-assert of `T1` in flight across a rotation to `T2` lands, generation still matches, `_registered` rolls back to `T1`, `unpair` owes the stale token, `T2` leaks; (3) the stated remedy is only “owe a `DELETE`,” paid at the **next** sign-in edge. That steal already exists in a tight window on `_register`; a resume `POST` hours into a session is how you take it to production. “Idempotent upsert… free and safe” is false the moment the `POST` crosses a logout. Idempotent for the same user; a reassignment for everyone else. You verified the reassignment at `a344943` and then priced it as a no-op.

**If RECAST, what to fold back:**
- **One `POST` door.** Every `registerDevice` — `start`, rotation, re-assert — enters the same tail. Skip-if-same is an opportunistic guard on the refresh path, not a wall the self-heal cannot pass (`force` / a sibling entry that shares the tail). A second copy of the 4-line block is guard six.
- **Finish the invariant.** After `await`, success **or** throw: if the issue-time generation is stale **or** the posted token is no longer desired, `remember` that token (fail toward deletion on a `POST` that might not have landed). `_generation` alone does not see rotation; desired-token is a different question, as you already ruled for permission vs island write.
- **Re-assert on evidence, not on a clock.** When `_attemptUnregister` completes (success or fail) and this object still holds `_registered == token`, **nudge** — do not `POST` from the DELETE path — the live door to restate the current pairing at the current `_generation`. Same nudge when a stale `POST` detects generation mismatch and `_registered != null`: a late upsert reassigned the row; B’s `DELETE` cannot undo it; only B’s `POST` takes it back. Resume + a throttle may remain a **backstop** for a `DELETE` that succeeded and then threw (unobserved over-delete). It is not the primary self-heal. Do not answer the already-foreground gap by setting the 6 to 0; that is how the knob becomes a correctness parameter and how a flaky network fills the isolate with uncancelled `POST`s (question F). Name the lifecycle: Flutter `resumed` does not fire for the session you are already sitting in.
- Strike “recovery drops to the next foreground” and “re-asserting is free and safe.” Honest bound: observed over-delete recovers in one live RTT; unobserved over-delete waits for backstop / next sign-in / process death; a `POST` in flight across an account switch is a reassignment, and the live pairing must restate or the previous owner’s mail rides the handset until the next session edge.

Three parts, two of them still deletions. The third is not a 6-hour prayer. The present is a clock; the future, for which the pairing actually has to work, is a live restatement at the moment the island has moved.
