## CarnotCodeCarver's Design Strike (round 2)

**Verdict:** RECAST

**Summary:** Cast 2 is close to the right thermodynamic direction: delete the repair branch, stop converting a bounded reach loss into an unbounded privacy write, and let live sessions restate truth. That is the colder, simpler engine. But the proof leaks heat at the exact place the author named: re-assertion can obey the register invariant only if it is a first-class forced POST with its own generation sample, post-await check, and timestamp semantics. As written, `_register` cannot be the whole mechanism because it suppresses same-token POSTs, and a stale-generation completion can create a durable DELETE debt against a token already live again. Feynman’s warning applies: “The first principle is that you must not fool yourself.” The design has not fooled itself about the old repair, but it is still underpricing the new writer.

**Fatal flaws:**
- A. Re-assertion is not automatically covered by `_register`. The existing `_register` returns early when `token == _registered`, which is exactly the steady-state case re-assertion exists to handle. So either re-assertion bypasses `_register`, becoming a new POST site that must prove the invariant separately, or `_register` needs a forced mode and timestamp update semantics. The design currently claims reuse of a mechanism that would skip the work.
- A/D. `_generation` distinguishes session incarnation, not desired row identity. Trace: session 1 reasserts T, logout bumps generation and records debt, session 2 starts and registers T, then the old reassert POST completes. Its post-await generation check fails and records a debt for T, even though T may now be the live desired row. That is fail-toward-deletion, but the document must name it: a stale successful POST can plant a future deletion of the current live pairing. This is acceptable only if explicitly priced as reach loss, not hidden under “covered.”
- The register invariant is incomplete on error paths. `_register` only owes a DELETE after a successful `await`; catch paths log or rethrow. But the design’s own repair analysis admitted that a lost response or ambiguous failure may still mean the island changed. If `registerDevice` can throw after the POST lands, the invariant must say which failures are known-not-landed versus maybe-landed. Otherwise under-delete is still possible after logout across an ambiguous POST failure.
- B. The asymmetry is directionally true but too absolute. Lost reach can be business-critical: calls, messages, safety alerts, MFA, care coordination. “Self-heals on next foreground after throttle” is not the same as “recovers” for a user who missed the only event that mattered. The design should keep the privacy-first ordering, but price deafness as a serious availability failure, not a cheap private inconvenience.
- E. `_reassertAfter = 6h` is a correctness-adjacent SLO knob, not merely a throttle. If over-delete is accepted because reassertion heals it, then the throttle bounds how long the handset can remain deaf after a foreground. If foreground happens at hour 1 and the last successful register was hour 0, the user may stay deaf for five more hours. That is not privacy correctness, but it is part of the safety case for reach.
- F. “App resume” is under-specified. Mobile lifecycle delivery is irregular across terminated apps, background isolates, OS force-stop, notification permission changes, web/desktop, and provider rebuilds. On flaky networks, foreground-triggered reassertion can become a bursty POST source unless single-flight/dedup/backoff semantics are named. Dijkstra’s line fits: simplicity is prerequisite for reliability, but an unnamed lifecycle hook is not yet simple.

**What holds:**
- Deleting the repair branch is the right subtraction. It removes the only POST proven to resurrect a signed-out handset after its DELETE debt was forgotten.
- The fail direction is correctly chosen for this domain: stale routable rows are privacy failures; over-deletion is primarily reach loss. Carnot would still ask for the efficiency table, but the hot and cold reservoirs are now in the right order.
- `drainPending` remains real work after the repair is deleted. It pays durable logout debts, and it is still the only client-side recovery for offline sign-out followed by a later session edge. It issues DELETEs with live credentials, but strict-before-start ordering keeps that from being a compensating write loop.
- The island handoff is correctly separated. Conditional unregister belongs server-side; no app-side choreography can make a stale DELETE no-op as fact.
- Keeping `_generation` is right. The permission-sheet and token-fetch windows still need a local liveness fence; deleting the repair does not delete that race.

**Fold back:**
- Define reassertion as an explicit forced register path, not an informal reuse of `_register`: sample `generation`, POST even when `token == _registered`, re-check after await, and update `lastSuccessfulRegisterAt` only if still current.
- Extend the REGISTER INVARIANT to cover ambiguous failures. Classify API outcomes as definitely-not-landed versus maybe-landed; for maybe-landed after stale generation, record debt. If the REST client cannot distinguish them, say so and fail toward debt.
- Name the stale-reassert-debt scenario as an accepted reach residual: an old reassert can complete after a new live session and plant a debt that later over-deletes the live row. The mitigation is the next reassert, not correctness by `_generation`.
- Make `_reassertAfter` an explicit reach SLO with a chosen bound, not just “start at 6 hours.” If six hours is acceptable, say why for this product; otherwise lower it or trigger immediate reassert on foreground when the app knows a DELETE straggler/debt event could have occurred.
- Specify lifecycle sources and blast-radius controls: which platforms call resume, whether start also reasserts, whether there is a single in-flight reassert, how failures back off, and whether repeated foregrounds can create concurrent POSTs.
- Keep the net deletion as the shape of the recast. Do not rebuild the reconciler. Fold these points into a smaller proof and then ship the subtraction. Hamming’s test is useful here: the purpose of computing is insight, not numbers; the purpose of this design is deletion, not another scheduler.
